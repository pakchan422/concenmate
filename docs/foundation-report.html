02 · 詳細發現

逐項診斷

按緊急程度排列——地基缺口優先處理，因為越遲補，將來搬動嘅成本越高。

F1 — 冇任何版本控制

地基缺口

位置：整個 concenmate/ 專案

現時嘅工作流程係逐次修改單一 index.html，再由你手動上傳去 GitHub Pages 覆蓋。冇 commit history，即係：

1) 唔知邊次改動令邊個功能壞咗；2) 冇辦法回滾去「上一個穩定版本」；3) 一旦你之外有第二個人同時改，兩份修改會直接互相覆蓋、冇任何合併機制。

影響：呢個係全份文件入面最急嘅一項——後面所有「交俾第二個人維護」嘅前提，都要建基於改動有紀錄、可追溯。

F2 — 單一巨型檔案，冇模組化

地基缺口

位置：index.html（10,839 行／594KB／320+ 個函式）

HTML、CSS、超過 300 個 JavaScript 函式全部寫喺同一個檔案入面，冇拆檔、冇建置工具（build tool）。呢個做法喺 project 細嗰陣（幾百行）完全冇問題，但已經去到萬行規模，會出現：新人要打開一個幾十萬字元嘅檔案先搵到自己要改嗰段；兩個人揀中同一段附近改，幾乎肯定撞版本控制嘅 merge conflict。

建議方向：唔使一步到位重寫，可以喺確立咗版本控制之後，逐步將功能拆做獨立檔案（例如 auth.js／room.js／admin.js），用輕量建置工具（例如 Vite）砌返做一個靜態網站部署。

F3 — 部署冇自動化、冇 staging 環境

地基缺口

位置：部署流程本身

每次改動經測試（如果有測試）之後，係直接推上正式網域 concenmate.com，即刻影響緊用緊嘅學生。冇一個獨立嘅「試驗場」畀新功能先落地驗證，亦冇任何自動化檢查（例如「呢個改動有冇令個網站整個爛咗」）喺推上線之前把關。

建議方向：最低成本做法係開多一個 GitHub Pages（或者 Firebase Hosting 嘅另一個 site）做 staging，配合獨立嘅 Firebase 開發用專案（或者 Firebase Emulator Suite 本機測試），新嘢試過冇問題先推正式站。

F4 — Firestore 單一文件逼近 1MB 上限

已解決（Phase 4）

位置：admin_config/gacha 文件，stickers[].photo 欄位

扭蛋機貼紙嘅相片全部以 base64 文字塞入呢一份 Firestore 文件嘅 stickers 陣列度。Firestore 每份文件有 1,048,576 bytes（1MB）嘅硬上限，base64 編碼仲會令原始檔案大約脹大 33%。貼紙越加越多，遲早會撞到呢個上限，到時新增貼紙會直接寫入失敗。

console.firebase.google.com → admin_config → gacha → stickers[0].photo = "data:image/jpeg;base64,/9j/4AAQSkZJRgA..."（單一欄位）

建議方向：將相片改存去 Firebase Storage，Firestore 淨係存一條短 URL——呢個已經喺前一輪對話入面詳細討論過，見下面路線圖 Phase 4。

Phase 4 完成更新（2026-09）：扭蛋機貼紙相片上傳已經全面改用 Firebase Storage（gacha_stickers/ 路徑），Firestore 淨係存返 download URL 字串。仲有全部 10 張已存在嘅貼紙相片都由 base64 手動重新上傳咗一次，令資料庫入面唔再存在任何 base64 長文字——admin_config/gacha 文件大細已經遠低於 1MB 上限，呢一項風險已解除。

F5 — 管理員名單要喺兩處手動同步

應盡快處理

位置：index.html 的 ADMIN_LOGIN_IDS（第 9480 行）同 firestore.rules 的 isAdmin()

管理員帳號 ID 要喺前端 index.html 同後端 firestore.rules 兩個檔案分別寫一份、手動保持一致——firestore.rules 檔案本身已經留咗註解提醒呢一點。萬一日後新增／移除管理員時漏咗更新其中一邊，會出現「介面顯示唔到管理後台入口，但實際權限仍然生效」或者相反嘅落差。

建議方向：將管理員名單改做存喺一份 Firestore 文件（例如 admin_config/adminIds），前端同 rules 都改讀返呢一個 source of truth，唔使兩處各自維護一份。

F6 — Firebase Storage 未有正式安全規則

已解決（Phase 4）

位置：Firebase 專案 concenmate-app 的 Storage bucket

專案設定入面已經有 storageBucket，但本機／專案資料夾入面搵唔到對應嘅 storage.rules。一旦按 F4 嘅建議開始用 Storage 擺相片，一定要喺開始用之前就寫好規則（邊個可以上傳、檔案大小上限、檔案類型限制），唔可以叫佢用 Firebase 預設值（預設好可能係「完全鎖死」或者「完全開放」其中一種極端）。

Phase 3 覆核更新（2026-09）：已經確認 index.html 而家完全冇用到 Firebase Storage SDK（getStorage／uploadBytes 等），Storage 喺 Console 度亦顯示未升級／未啟用——即係話呢一項暫時冇實際風險，唔需要而家就升級去 Blaze 收費方案去寫規則。呢一項正式挪去 Phase 4（資產／資料庫瘦身），到時決定將圖片搬去 Storage 嗰刻先一併處理。

Phase 4 完成更新（2026-09）：concenmate-dev 同 concenmate-app 兩個專案已經雙雙升級去 Blaze 方案（配合預算提醒：dev HK$25／prod HK$50），並已部署正式 storage.rules——白名單制，淨係 admin（集中讀 admin_config/adminIds）先可以寫入／刪除，讀取要求已登入，檔案大小同類型都有限制。同時加設咗 App Check（reCAPTCHA Enterprise）加多一層防護。呢一項風險已解除。

F7 — 冇任何自動化測試

應盡快處理

位置：整個專案

所有驗證（例如番茄鐘循環、開咪冷卻時間）目前靠人手逐次開瀏覽器試，或者對話過程中臨時寫嘅一次性腳本，跑完即棄，冇留低任何可以重複執行嘅測試。呢個做法喺功能少嗰陣夠用，但函式一多，「改咗 A 度但唔知有冇整壞 B」嘅風險會愈嚟愈高。

建議方向：唔使一開波就追求全面覆蓋，可以由最關鍵、最容易私自出錯嘅邏輯開始（計分／時數累積、番茄鐘循環、管理員權限判斷）寫低幾條可重複執行嘅測試。

F8 — 安全規則本身思路紮實，值得保留

值得肯定

位置：firestore.rules

呢份規則檔本身寫得比預期紮實：分開咗 get／list 權限（防止用戶批量爬取全部人資料）、鎖死咗 loginId 唔可以自己改（防止假扮管理員）、對 exp／hours／points 嘅單次改動幅度都有設上下限（防止用開發者工具直接篡改分數）。每條規則仲附有解釋緣由嘅註解，呢個係好多正式公司 project 都做唔到嘅水平，值得保留同延續呢種寫法。

F9 — 前端計分邏輯屬已知、可接受嘅階段性限制

未來優化

位置：awardStudyPoint() 同對應嘅 rules 止血檢查

計分／經驗值本身喺前端計算，理論上熟悉開發者工具嘅人都可以嘗試篡改——但目前規則檔已經對單次改動幅度封頂，令呢種攻擊最多只可以「慢慢刷」，唔可以一次過跳到極端數值。要徹底杜絕就要將計分邏輯搬去 Cloud Functions 由伺服器驗證，屬於下一個成熟度階段先值得投放嘅工夫，現階段唔算逼切。

F10 — EmailJS 網域白名單屬付費方案專用功能，已知並接受呢個限制

已知限制・接受

位置：EmailJS 帳戶（dashboard.emailjs.com）→ Account → Security → Domains

Phase 3 覆核 EmailJS 後台時發現：「限制邊啲網域先可以用個 public key 寄信」呢個功能，喺免費方案（Free tier）根本撳唔到「Save Changes」——會彈出「You have reached your subscription limit. Please upgrade to unlock this feature.」，即係話呢個功能對免費戶口嚟講係完全鎖死嘅收費功能，唔係「設定漏咗」，而係「設定唔到」。

實際風險評估：因為 index.html 入面嘅 EmailJS public key 本身係公開設計（任何人睇網站原始碼都見到，呢個唔算資料外洩），最壞情況係第三方攞呢條 key 去自己網站亂咁寄信，透支呢個帳戶每月 200 封嘅免費配額，令 concenmate.com 真正嘅驗證郵件暫時寄唔出，要等落月配額重置。呢個唔會導致資料外洩，亦唔會產生額外費用（免費方案冇「超額自動找數」）。

決定：因為風險屬「有機會小小唔方便，但唔算高危」，暫時唔為呢一項升級 EmailJS 收費方案（大約幾美金一個月）。如果日後真係持續見到配額被異常透支（例如 Email History 見到大量唔認得嘅收件人），先重新評估升級。
